## 1. 总体判断

后端已经形成可运行的轻量六边形架构和较完整测试基线。输入检测、模型转发、工具意图归因、风险评分、任务链分析、策略判定、分级处置、执行和审计可以串成端到端链路。主要问题不在“有没有功能”,而在生产安全默认值、流式助手时序、授权令牌防重放、跨请求安全状态和执行隔离强度。

## 3. 真实请求链路

[核心管线](../../src/fulcrum/core/pipeline.py) 当前按以下顺序处理:

1. 标注输入来源类型和信任等级。
2. 执行多个检测器并聚合 Finding。
3. 通过输入闸门决定放行、净化、审批或阻断。
4. 将通过的请求转发给模型。
5. 解析工具意图并进行证据化来源归因。
6. 计算工具固有风险和参数风险。
7. 分析当前请求内的动作链。
8. 使用 YAML 策略判定。
9. 执行 `allow/sanitize/approve/block` 分级处置。
10. 对工具返回和模型输出执行出口检测。
11. 将关键节点写入 append-only hash-chain 审计。

安全关键阶段的未处理异常总体采用 fail-closed。未知工具即使被策略意外放行,执行前仍会显式阻断。

## 4. 默认装配

默认配置是开发和确定性演示基线,不是生产强化基线:

```yaml
labeler: role_trust
detectors:
  - keyword_rules
  - secret_egress
  - manifest_guard
  - disclosure_egress
  - exfil_channel
attributor: evidence
risk_scorer: heuristic
chain_analyzer: sequence
policy: yaml
executor: restricted
tools:
  - echo
model: fake
audit: memory
```

由此必须区分:

- 规则检测器是默认能力。
- ML classifier 和 LLM Judge 有实现,但属于可选能力。
- `file.read`、`file.write` 有实现,但默认只注册 `echo`。
- SQLite 审计有实现,但默认审计 sink 是内存。
- 真实 OpenAI 兼容模型可配置,但默认模型是 `fake`。

## 5. 已实现能力

### 5.1 输入和输出检测

- Unicode NFKC、零宽字符、同形字、leet 和双向文本处理。
- Base64、Base32、Hex、URL、HTML entity 等多层解码复扫。
- 中英文提示注入、越狱、命令、外泄和良性上下文抑制规则。
- PII、密钥、连接串、JWT、云凭据和私钥检测。
- 策略原文、工具 schema、系统提示和外带通道检测。
- manifest 请求内哨兵。
- 可选 ML classifier 和本地/兼容模型 LLM Judge。

注意:核心管线会把检测器抛出的异常转为 critical `detector_error`;但 ML/Judge 适配器对部分加载或推理错误在内部降级为 noop。因此准确表述应为“确定性基线保持运行并由规则层兜底”,而不是“任何语义检测后端故障都会自动阻断”。

### 5.2 来源归因和任务链

`EvidenceAttributor` 会从工具参数生成原值、去 scheme 核心、路径、主机、IP 和敏感令牌等结构化种子,与各来源内容匹配,按信任等级和证据强度排序。

它是可解释的 evidence-based attribution,不是形式化信息流或 taint 证明。

`SequenceChainAnalyzer` 已覆盖:

- 敏感读取后外发。
- 工具返回后编码再外发。
- 工具返回后写入长期记忆或知识库。
- 获取、落盘再执行。

当前链分析只覆盖单个 `Context` 生命周期。`request_trace` 和 `tool_returns` 不跨请求持久化,尚无 `SessionTraceStore` 或等价安全状态端口。

### 5.3 策略和受限执行

YAML 策略可引用工具集合、风险阈值、来源信任、敏感路径、工作区越界、SSRF、域名白名单、危险命令、破坏性动作和任务链模式。

`RestrictedExecutor` 在执行前复查路径、软链接、命令、协议、域名、输入体积,并通过线程池调用同步工具、限制等待时间和截断超大输出。

它不是进程或容器沙箱:

- 超时只停止调用方等待,工作线程可能继续。
- 已经发生的写盘或外联副作用无法撤销。
- 连续超时可能占满线程池。
- 没有 seccomp、系统调用过滤、进程级资源隔离或独立网络命名空间。

### 5.4 审计

已实现内存和 SQLite 两种 sink、每会话独立 hash-chain、可选 HMAC-SHA256、版本化哈希字段、SQLite 串行追加、WAL 和首个断链点定位。

生产边界:

- 默认是内存 sink,重启后丢失。
- 默认未配置 HMAC,裸 SHA256 不能防止拥有数据库修改权限的人重写整条链。
- 当前没有报告中所写的“审计失败本地重试队列”。
- 全链验证和部分全量读取在数据增长后可能成为同步热点。

### 5.5 登录、会话与 RBAC

已实现 Argon2 口令哈希、服务端随机会话 token、token hash 入库、HttpOnly Cookie、登录失败锁定、待审批/停用/离职状态、部门树、角色、权限点、多团队 membership 和团队负责人范围。

同时实现:

- 防止停用最后一个超级管理员。
- 角色变化、停用和重置密码时使已有会话失效。
- 防止操作者向他人授予自己没有的组织级权限。
- 团队负责人只能管理本团队子树。

生产边界:

- Cookie `Secure` 默认是 false。
- `/v1/chat/completions` 和 `/tools/call` 不走控制台 Cookie 会话鉴权。
- `/gateway/chat` 只有配置 `FULCRUM_GATEWAY_API_KEY` 后才要求网关密钥;默认空值意味着开发态开放。

### 5.6 AI 操作助手

已实现多轮 function-calling、按 RBAC 过滤工具、读取自动执行、写操作提案确认、撤销、会话历史落盘、旧对话压缩、渐进式工具发现,以及 OpenAI/Ollama/Anthropic 三类协议。

助手具备输入、工具返回和输出自防检测,但仍有四个高优先级问题:

1. 流式模型 `delta` 在完整出口检测前已经发送,存在先泄露后覆盖。
2. Action Token 只绑定工具、操作者和过期时间,未绑定会话、参数摘要或一次性 nonce,确认接口可在有效期内重放。
3. Undo 记录保存原操作者,执行撤销时却未比较当前主体与原操作者;同权限用户获得 `action_id` 后可能撤销他人操作。
4. 会话锁只包围最终保存,没有覆盖完整的“加载历史—模型推理—保存”临界区;同会话并发请求可能发生后写覆盖。

另外,`UndoStore._records` 和 `ConversationStore._locks` 没有 TTL/LRU 清理;新 Agent 注册表与旧 `catalog.py`/前端 action seed 仍是双轨来源。

## 7. 优先级建议

### P0

1. 把助手流式出口闸门改为先判定后发送,补充敏感字节零泄露测试。
2. 为确认 token 加入一次性 nonce、参数摘要、会话/请求绑定和消费记录。
3. Undo 强制校验原操作者或明确的管理员代操作权限。

### P1

1. 生产配置启动时 fail-fast:要求网关鉴权、持久化审计、HMAC、Secure Cookie 和真实模型配置。
2. 引入跨请求 `SessionTraceStore` 或等价安全状态,再声称跨会话污染追踪。
3. 将高风险工具执行迁移到可终止的子进程或容器隔离边界。
4. 将助手会话锁覆盖完整读—推理—写过程,并清理无界内存状态。

### P2

1. 拆分 `assistant/operations.py`。
2. 统一助手操作注册表,逐步淘汰旧 catalog/action seed 双轨。
3. 为审计大数据量查询、全链验证和失败重试定义持久化方案。
