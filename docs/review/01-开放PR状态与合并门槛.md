## 5. 未采纳项留档

**`llm_judge` 进默认 `detectors`(#131)**:启用后每条输入都会打一次真实模型端点,P95 从 ~3ms 升到 ~575ms,且输入内容外发到该端点。对"数据不出域"这条政务红线,这是需要部署方按合规口径显式决策的开关,不应随一个评测 PR 默认打开。端点经 `.env` 注入的链路保留,放开 `fulcrum.yml` 中一行即生效;`docs/eval/01-LLM-Judge准入基准.md`(#122)是该决策的依据文档。

## 6. 合并门槛

1. 分支必须 rebase 到最新 `origin/dev`,并解决冲突;不得以旧分支的整体文件覆盖新基线。
2. **对 `docs/plan/03-进度看板.md` 的追加要格外小心**:基于旧基线的分支会**无冲突地**删除新基线上的变更记录(#121/#132 都发生过),`git merge-tree` 试合才能发现。建议功能 PR 不改该文件,合并时由维护者统一补一行 —— 目前绝大多数 PR 冲突都出在这里。
3. 通过与变更范围匹配的单元、接口和安全回归测试;高风险执行器、配置热替换和审计路径必须有失败场景测试。
4. 涉及指标的 PR 必须记录数据集版本、运行命令、模型/端点、策略和生成时间,并与主结果分开保存。**PR 描述里的历史数字不作为合并依据**,须在当前 `dev` 上重测。
5. 全量评测不出现主基线召回、FPR、Utility 或处置准确率回退;新检测器需要提供按攻击类型和闸门分域结果,并证明**在当前基线上**存在增量。
6. 改动冻结语料必须同步 bump `VERSION` + 写 `CHANGELOG.md` + 更新 `DATASHEET.md`,否则既有指标失去可比性。
7. 安全边界变更必须说明 fail-closed/fail-safe 行为、旁路风险和生产部署限制;注释所声明的失败语义必须与代码实际行为一致。
8. 新增 `docs/plan/NN-` 文档前先确认编号未被占用(已发生三次撞号)。
