## 0. 核心模型:组织 ≠ 权限 ≠ 职位

参照飞书 / 钉钉 / Okta / Azure AD 的成熟做法,把三件常被混为一谈的事拆开,这是整个设计的地基:

| 概念 | 回答 | 形态 | 决定权限? |
| --- | --- | --- | --- |
| **部门(组织归属)** | 你坐在哪个团队、向谁汇报 | 可嵌套的组织树 | 否 |
| **系统角色** | 你在本系统里能做什么 | 权限点集合,与部门正交 | **是** |
| **职位(title)** | 名片上的头衔 | 一段文本 | 否 |

> 为什么正交:安全运营部里既有"运营员"也有"部门主管";同一个角色"审计员"可能分散在多个部门。把组织和权限绑死,真实组织一变动就处处掣肘。

## 1. 权限点(permission)—— RBAC 的最小粒度

权限点**由系统代码定义**(见 [`permissions.py`](../../src/fulcrum/adapters/auth/permissions.py)),不能由用户凭空发明 —— 因为每个点都对应后端某个受保护操作 / 前端某个功能模块。管理员能做的是**新建或调整角色 → 从目录里勾选权限点**。

- 命名:`<域>.<动作>`。`*.view` 控"能否看到该模块"(前端导航/路由按它过滤);`*.manage`/`*.handle`/`*.run`/`*.approve` 控具体操作。
- 权限点按影响面分组(监测/管控/取证/成员与权限/系统配置)。关键系统域:`users.view`/`users.manage`(成员)、`dept.manage`(组织)、`roles.manage`(角色)、`account.approve`(审批)、`ai.operate`(AI 操作助手)、`ai.configure`(AI 模型配置)。

## 2. 内置角色(6 档,可调整)

空库首次启动时种子化 6 档预置角色,`is_system=true` 只表示"系统预置来源",不是锁定标记。拥有 `roles.manage` 的管理员可以修改其权限、名称与描述,也可以删除未被成员使用的内置角色。启动种子不会覆盖管理员后续调整;在用角色仍需先改派成员才能删除。

| 角色 | 定位 | 权限 |
| --- | --- | --- |
| 超级管理员 | 系统拥有者 | 全部权限 |
| 系统管理员 | 日常管理 | 除 `roles.manage` 外全部 |
| 安全主管 | 统筹研判 | 看全局 + 处置/审批/发起评测 + AI 操作助手 |
| 安全运营员 | 一线值班 | 监测处置 + 看管控取证 + AI 操作助手 |
| 审计员 | 只读取证 | 审计/评测只读 + AI 操作助手 |
| 只读访客 | 只读 | 仅业务看板只读,默认不含 AI 操作助手 |

**自定义角色**:管理员新建,勾选权限点,可改可删(在用角色需先改派才能删)。

## 3. 组织架构(可嵌套树)

种子是典型政企安全运营组织,可随意改名/增删:

```
信息安全中心
├── 安全运营中心(SOC) ── 7×24 监控值班组 / 应急响应组(IR)
├── 安全管理与合规组(GRC)
├── 攻防与威胁情报组
└── 安全平台与运维组
```

- 部门 CRUD 带护栏:**防自身成环**(不能移到自己的子树下)、**防删非空**(有子部门或成员时拒删)。
- 选父部门即看到其整棵**子树**的成员(`subtree_ids` 展开)。

## 4. 成员与生命周期

成员字段:账号 · 姓名 · 工号 · 邮箱 · 手机 · 职位 · 部门 · 角色 · 状态 · 最后登录。
状态机:`pending`(待审批)→ `active`(在职启用)↔ `disabled`(停用);`left`(离职)为终态。非 `active` 一律不能登录。

管理动作(均在 [`DirectoryService`](../../src/fulcrum/adapters/auth/directory.py)):新增 · 编辑资料 · 调岗(换部门) · 改角色 · 停用/恢复 · 离职 · 重置口令 · 审批/驳回。**真实安全护栏**:

- **防自锁**:不能停用/离职/改派**最后一个在岗超级管理员**。
- **改权即生效**:改角色 / 停用 / 重置口令时,**踢掉该用户全部在途会话**,强制重登 —— 权限变更不留窗口期。
- **临时口令**:管理员直建成员、或重置口令时不填明文 → 系统生成强随机临时口令,**仅这一次**经响应返回并在前端弹窗展示,提示尽快转交并改密。

## 5. 申请 → 审批流(私有化、无邮件)

私有化部署没有邮件系统,新成员入场走"自助申请 + 管理员审批":

1. 登录页「申请账号」:申请人自填**姓名 + 账号 + 口令** → `POST /auth/register` 落为 `pending`。
2. 待审批账号**不能登录**(登录返回 403「待审批」,且口令正确后才暴露此状态,不泄露账号是否存在)。
3. 有 `account.approve` 权限的管理员在「待审批」页签**分派角色 + 部门**后批准 → 转 `active`,即可登录;或**驳回**(删除该申请记录)。

> 口令在申请时由本人设定,审批只做激活与分派 —— 管理员无需经手他人明文口令。

## 6. 强制点:访问控制在后端

**前端按权限隐藏菜单只是体验,真正的闸门在后端。**

- 后端:每个受保护接口用 `require_permission(点)` 声明所需权限([`deps.py`](../../src/fulcrum/adapters/api/deps.py));无会话 → 401,有会话但缺权限 → 403。越权请求即使绕过前端也被挡下。`/auth/me` 返回当前主体的**生效权限点集合**。
- 前端:`FeatureModule.requires` 声明模块所需权限;`getFeaturesFor(权限)` 过滤导航与路由 → **不同权限看到不同界面**。用户管理页本身受 `users.view` 守卫,「待审批」页签受 `account.approve` 守卫,各管理动作按 `users.manage`/`dept.manage`/`roles.manage` 显隐。

## 7. 接口一览

| 方法 | 路径 | 权限点 | 说明 |
| --- | --- | --- | --- |
| POST | `/auth/register` | 公开 | 申请账号(落 pending) |
| GET | `/admin/permissions` | `users.view` | 权限点目录 |
| GET·POST·PATCH·DELETE | `/admin/departments[/{id}]` | view / `dept.manage` | 组织架构 CRUD |
| GET·POST·PATCH·DELETE | `/admin/roles[/{id}]` | view / `roles.manage` | 角色与权限 CRUD |
| GET | `/admin/users` · `/admin/users/stats` | `users.view` | 成员列表(按部门子树/状态/角色/搜索)+ 统计 |
| POST·PATCH | `/admin/users[/{id}]` | `users.manage` | 新建 / 改资料调岗调权 |
| POST | `/admin/users/{id}/status` · `/reset-password` | `users.manage` | 停用恢复离职 / 重置口令 |
| POST | `/admin/users/{id}/approve` · `/reject` | `account.approve` | 审批 / 驳回 |

## 8. 存储

复用登录的 SQLite 库([`auth_db_path`](../../.env.example),默认 `data/runtime/auth.sqlite`):新增 `departments` / `roles` / `role_permissions` 表,`users` 表扩展组织/角色/资料/状态列。对登录模块 v1 的旧 `users` 表做**列级迁移**(`ALTER TABLE ADD COLUMN`),不丢历史数据。

## 9. 边界与后续

- 本模块把 [控制台能力规划](../plan/05-控制台能力规划.md) 里"先做 RBAC"的设想**落到实处并已强制生效**(此前登录文档中"本期不含 RBAC"的说明就此更新)。
- **自助改密**(个人中心)未做:当前改密走管理员"重置口令"。
- 管理动作目前走结构化日志;接入 hash-chain 审计为后续项。
- 前端隐藏不等于安全 —— 任何新增的受保护接口都必须挂 `require_permission`,这是不可省的红线。
