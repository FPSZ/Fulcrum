# 网关算法架构复核

> 本文回答什么问题:当前枢衡网关算法架构是否合理,哪些地方是核心优势,哪些地方存在架构短板,以及应优先让 Claude 复核哪些判断。
> 状态:草稿 v1,待复核。
> 范围:仅分析后端网关算法与安全判定链路,不评价前端页面、视觉设计和阶段性计划。

---

## 1. 当前算法架构判断

当前网关不是单一模型判定,也不是简单关键词拦截,而是一条多层安全判定链:

```text
用户输入
  -> 输入检测器
  -> 输入闸门 screen_input
  -> 上游企业智能体
  -> 出口检测器
  -> 出口闸门 screen_output
  -> 返回用户

工具调用
  -> 证据归因
  -> 工具风险评分
  -> 请求级任务链分析
  -> YAML 策略判定
  -> 执行 / 净化 / 待审批 / 阻断
  -> 审计留痕
```

对应代码位置:

| 链路 | 代码位置 | 职责 |
|---|---|---|
| 输入/出口闸门映射 | `src/fulcrum/core/gateway.py` | 将 `Finding.score` 映射为 `allow / approve / block / sanitize` |
| `/gateway/chat` 编排 | `src/fulcrum/adapters/api/app.py` | 输入检测、上游转发、出口检测、结果回传 |
| 管线编排 | `src/fulcrum/core/pipeline.py` | 检测、归因、评分、链分析、策略、执行、审计 |
| 规则检测器 | `src/fulcrum/capabilities/detectors/keyword_rules.py` | 注入、越狱、外泄、命令、投毒、PII 等确定性检测 |
| 证据归因 | `src/fulcrum/capabilities/attribution/evidence.py` | 用参数片段和来源内容建立可解释归因边 |
| 工具风险评分 | `src/fulcrum/capabilities/toolguard/heuristic.py` | 根据工具基础风险和参数风险计算动作危险度 |
| 任务链分析 | `src/fulcrum/capabilities/toolguard/sequence_chain.py` | 识别读取到外发、工具返回到外发、工具返回到长期记忆写入 |
| 策略引擎 | `src/fulcrum/capabilities/policy/yaml_policy.py` | 根据来源、风险、链路、路径、域名、命令等事实分级处置 |
| 默认策略 | `data/policies/default.yml` | 当前默认处置规则和白名单 |

总体判断:当前方向合理,已经具备“智能体安全网关”的核心形态。真正的算法价值不在 `gateway.py` 的阈值判断本身,而在检测器、来源信任、证据归因、工具风险评分、任务链分析和声明式策略的组合。

## 2. 架构优势

### 2.1 输入和出口双闸门是必要设计

`/gateway/chat` 先执行 `screen_input`,只有输入判定为 `ALLOW` 才转发给上游企业智能体。上游回复回来后再执行 `screen_output`,用于拦截模型输出中的敏感数据泄露、策略泄露或危险内容。

这个设计符合智能体安全网关的基本要求:不能只查用户输入,还必须检查模型和智能体最终吐给用户的内容。

### 2.2 检测和处置解耦

`src/fulcrum/core/gateway.py` 只做处置映射,不直接写检测规则:

```text
detectors -> Finding(score, kind, evidence) -> screen/screen_output -> Disposition
```

好处:

- 后续新增检测器不需要改网关主流程。
- 规则检测、小模型检测、LLM judge 可以并列产出 `Finding`。
- 策略阈值和检测逻辑可以分开调参。
- 审计可以统一展示 `Finding` 证据。

### 2.3 工具调用治理链路比较完整

工具调用走独立安全链:

```text
ToolIntent
  -> EvidenceAttributor
  -> HeuristicRiskScorer
  -> SequenceChainAnalyzer
  -> YamlPolicyEngine
  -> Executor
```

这比简单工具黑名单更合理。因为智能体攻击常见问题不是“某个工具绝对危险”,而是“不可信来源驱动了某个高风险动作”,或者“多个单步合法动作组合成外泄链”。

### 2.4 任务链分析有差异化价值

`SequenceChainAnalyzer` 能识别三类关键风险:

- `chain.taint_exfiltration`:外发参数确实携带上一步工具返回内容。
- `chain.exfiltration`:读取后外发,敏感读取后外发更高危。
- `chain.persistence_poisoning`:不可信工具返回写入长期记忆或知识库。

这是智能体安全里比普通 prompt injection 检测更关键的部分。单步工具调用可能都看起来合理,但组合起来才构成外泄或投毒。

### 2.5 策略外置有利于政企场景

`YamlPolicyEngine` 将处置逻辑放到 YAML 策略中,支持按来源信任、工具、风险分、链风险、路径、域名、命令等事实做组合判定。

这对政企场景重要,因为不同单位的白名单域名、敏感路径、审批策略、默认拒绝策略可能不同。策略外置比把规则写死在代码里更可维护。

### 2.6 fail-closed 意识较好

`SecurityPipeline` 在检测器异常、归因/评分/链分析/策略异常、未知工具、执行异常等安全关键位置都倾向 fail-closed,不会静默放行。

这个设计对安全网关很关键。评审时可以强调:安全关键路径失败时默认阻断并审计,而不是为了可用性直接放过。

## 3. 主要问题和不合理点

### 3.1 网关阈值层本身算法贡献较薄

`gateway.py` 的核心是固定阈值:

```text
score >= 0.8 -> block
score >= 0.6 -> approve
else         -> allow
```

这在工程上合理,但如果对外说“网关算法就是这个”,会显得算法太薄。当前真正的算法贡献在多检测器、来源信任、归因、风险评分、任务链分析和策略组合。

建议表述:

> 网关处置层使用阈值映射,但完整判定由多源检测、来源信任加权、证据归因、工具风险评分、任务链分析和声明式策略共同完成。

### 3.2 `max_score` 与实际生效风险分可能不一致

`gateway.py` 里 `_effective_score()` 会把多来源分片风险抬升到复核档,但 `GateVerdict.max_score` 仍返回原始最高分,不是等效分。

可能出现:

```text
max_score = 0.4
decision = approve
```

这对 UI、审计、评测解释都不友好。用户会疑惑为什么 0.4 也进入人工审核。

建议:

- 在 `GateVerdict` 增加 `raw_score` 和 `effective_score`。
- 审计 evidence 中同时记录 `raw_score`、`effective_score`、`aggregation_reason`。
- 前端展示“最高单项风险”和“综合风险”两个概念。

优先级:高。改动小,解释收益大。

### 3.3 多来源分片防御只升到复核,严格场景可能偏软

当前逻辑:

```text
多个不同来源命中 medium 以上
  -> 最高只升到 REVIEW_AT
  -> 不会因为聚合直接 block
```

这降低误伤,但对强攻击可能偏软。例如多个来源分别命中:

```text
injection + exfiltration + sensitive_file
```

这种组合已经具备明显攻击意图,严格政企模式下可以考虑直接阻断。

建议:

- 默认模式保持当前保守策略。
- 增加 strict profile:
  - 多来源分片 + 高危类别组合 -> block
  - 多来源分片 + 仅中风险类别 -> approve

优先级:中。

### 3.4 任务链分析目前是请求级,不是会话级

`SequenceChainAnalyzer` 当前只看 `Context.request_trace`,窗口是 `_WINDOW = 12` 个工具步骤。代码注释也说明这是请求级序列,跨请求链待扩展。

风险:

- 攻击者可以把读取和外发拆到不同请求。
- 多轮智能体任务中的长期链路无法完整识别。
- 记忆投毒可能跨会话生效,但当前链分析不维护长期安全状态。

建议新增 `SessionTraceStore` 或 `SecurityStateStore`:

```text
session_id
  -> 最近 N 步工具调用
  -> 工具返回摘要 / 哈希 / 可比对片段
  -> 上一次高风险读取
  -> 上一次不可信工具返回
  -> 长期记忆写入记录
```

链分析器从“请求级 trace”升级为“请求级 + 会话级 trace”。

优先级:高。这是智能体安全算法架构的关键增强。

### 3.5 工具语义识别依赖工具名和参数键,扩展性不足

`SequenceChainAnalyzer` 判断读、外发、持久化写入时大量依赖工具名正则和参数键:

```text
read/search/query/fetch -> read
send/post/upload/http   -> outbound
remember/memory/kb      -> persist
url/to/endpoint         -> destination
```

这能支撑 MVP,但插件化扩展时不稳定。队友新增工具如果命名不规范,可能绕过链分析。

建议让工具声明能力元数据:

```python
capabilities = {
    "data.read",
    "network.egress",
    "filesystem.read",
    "filesystem.write",
    "memory.write",
    "shell.exec",
    "destructive",
}
```

任务链分析优先读工具元数据,正则只作为 fallback。

收益:

- 队友新增工具时只声明能力,不用改核心正则。
- 策略可以基于能力而不是具体工具名。
- 更符合“后续通过插件扩展,不动核心”的架构目标。

优先级:高。

### 3.6 默认策略 `default: allow` 对生产严格场景偏宽

`data/policies/default.yml` 当前默认未命中规则时 `allow`。这对开发和演示友好,但政企安全网关生产模式下可能偏松。

建议至少提供两套策略:

| 策略 | 用途 | 默认行为 |
|---|---|---|
| `default.yml` | 开发和演示 | 未命中规则允许 |
| `strict.yml` | 政企严格模式 | 未知工具、未知来源、高风险不确定项进入审批或阻断 |

尤其要关注:

- 未知工具能力。
- 无来源归因但动作高风险。
- 非白名单外联。
- 写长期记忆。
- 执行系统命令。

优先级:中高。

### 3.7 归因是证据匹配,不是形式化 taint

`EvidenceAttributor` 通过参数片段和来源内容匹配建立归因边。这是务实、可解释的设计,但它不能覆盖语义改写、摘要、翻译、多跳推理。

建议文档和答辩中保持准确表述:

> 当前归因是 evidence-based attribution,不是形式化 taint tracking。系统给出可解释证据和置信度,不声称严格证明参数一定来自某段输入。

后续可以增加:

- semantic attribution。
- LLM judge 归因解释。
- attribution hit@1 / hit@3 评测。

优先级:中。

### 3.8 规则检测层低延迟、可解释,但语义泛化能力有限

`KeywordRuleDetector` 覆盖了中文政企场景下很多风险,并做了归一化、混淆解码、间接来源加权、PII 计数等增强。

但规则层天然存在短板:

- 语义改写攻击可能漏。
- 长上下文策略操控可能漏。
- 没有明显关键词的社会工程式注入可能漏。
- 新型攻击需要持续补规则。

建议把算法分层明确为:

```text
L1 确定性规则:低延迟、可解释、低成本
L2 行为链分析:识别工具序列和组合风险
L3 可选语义判别:LLM judge / 小模型,提升召回
L4 策略治理:按政企要求分级处置
```

优先级:中。

### 3.9 出口净化目前只特判 `pii_leak`

`screen_output()` 只有当风险集合正好是 `{"pii_leak"}` 且分数处于复核档时,才做 `SANITIZE`。

这是安全保守的设计,但后续可以扩展成“可净化风险类型注册表”:

| 风险类型 | 可选净化动作 |
|---|---|
| `pii_leak` | 结构化脱敏 |
| `secret_leak` | 密钥打码 |
| `markup_exfil` | 移除或中和 markdown/HTML 外联 |
| `tool_list_leak` | 删除敏感工具和策略片段 |

优先级:低到中。先不要过度做,但架构上可以预留。

### 3.10 `APPROVE` 更像软阻断,审批闭环需要确认

当前 `APPROVE` 的语义是挂起待审批,不转发或不执行。但如果没有完整审批队列、审批通过后的重放机制、审批超时策略,它在实际产品中更接近“软阻断”。

建议 Claude 重点核实:

- 是否已有审批队列。
- 审批证据是否足够。
- 审批通过后如何恢复执行。
- 审批超时默认 fail-closed 还是 fail-open。

优先级:中。它不一定影响算法本身,但影响安全治理闭环。

## 4. 建议优先级

### P0:建议先做

1. 给 `GateVerdict` 和审计 evidence 增加 `effective_score`。
2. 给工具增加能力元数据,链分析优先基于工具能力而不是工具名正则。
3. 设计会话级 `SessionTraceStore`,支持跨请求任务链分析。

### P1:建议较快做

1. 增加 `strict.yml` 策略包。
2. 明确归因不是形式化 taint,补 attribution 指标。
3. 将算法架构分层写清楚:规则层、链分析层、语义增强层、策略处置层。

### P2:后续增强

1. 将出口净化从 `pii_leak` 特判升级为可注册净化器。
2. 给多来源分片防御增加严格模式。
3. 完善人工审批闭环和审批超时策略。

   关注规则检测、来源信任加权、间接来源加权、混淆解码、PII 计数。

5. src/fulcrum/capabilities/attribution/evidence.py
   关注证据归因是否只是 evidence-based attribution,是否存在语义改写漏归因问题。

6. src/fulcrum/capabilities/toolguard/heuristic.py
   关注工具风险评分是否合理。

7. src/fulcrum/capabilities/toolguard/sequence_chain.py
   关注任务链分析是否只支持请求级 trace,是否应扩展为会话级 trace;同时看工具语义识别是否过度依赖工具名正则。

8. src/fulcrum/capabilities/policy/yaml_policy.py 和 data/policies/default.yml
   关注策略外置、默认 allow、strict profile 是否必要。

请判断以下观点是否成立,并指出不同意的地方:

1. 当前网关算法架构方向是合理的,不是简单关键词拦截,而是“检测器 + 来源信任 + 证据归因 + 工具风险评分 + 任务链分析 + 声明式策略”的组合式安全判定。

2. gateway.py 的阈值映射层本身算法贡献较薄,真正算法价值在检测器、归因、链分析和策略组合。

3. GateVerdict 只返回 max_score,但 _effective_score 会影响最终处置,因此应增加 raw_score / effective_score / aggregation_reason,否则 UI 和审计可能出现“0.4 分却 approve”的解释问题。

4. 多来源分片防御现在只升到 approve,默认保守合理;但 strict 策略下可以允许高危类别组合直接 block。

5. SequenceChainAnalyzer 当前是请求级链分析,对跨请求、多轮智能体攻击覆盖不足,应引入 SessionTraceStore 或 SecurityStateStore。

6. 任务链分析用工具名正则和参数键判断 read/outbound/persist,对插件扩展不够稳,应让工具声明 capabilities,链分析和策略优先基于能力元数据。

7. default.yml 的 default: allow 适合开发和演示,但政企生产应提供 strict.yml,对未知工具、未知来源、高风险不确定项默认 approve 或 block。

8. EvidenceAttributor 是务实的证据匹配归因,不是形式化 taint tracking。文档和答辩中应避免过度声称“严格污点追踪”。

9. KeywordRuleDetector 低延迟、可解释,但语义泛化能力有限;算法架构应明确“确定性规则 + 行为链分析 + 可选语义 judge”的分层。

10. screen_output 目前只对 pii_leak 做 SANITIZE,安全保守但范围较窄;后续可抽象成可注册净化器。

## 6. 复核结论摘要

当前网关算法架构可以成立,并且比单点 prompt guard 更完整。最值得强调的是三点:

1. 前置输入闸门和出口闸门形成闭环。
2. 工具调用不是黑名单,而是归因、评分、链分析、策略组合。
3. 任务链分析覆盖了“单步合法、组合危险”的智能体攻击特征。

当前最需要补强的是三点:

1. 解释一致性:补 `effective_score`。
2. 扩展一致性:工具语义从正则猜测升级为能力元数据。
3. 攻击链完整性:请求级链分析升级到会话级链分析。
