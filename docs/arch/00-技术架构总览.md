## 1. 架构目标与约束

| 约束                               | 来源          | 对架构的要求                              |
| ---------------------------------- | ------------- | ----------------------------------------- |
| 无侵入、兼容 OpenClaw 类智能体     | 榜题 / 大方向 | 旁挂式接入,不改被保护智能体内部           |
| 一体化闭环(评测—防护—审计—运营) | 大方向差异化  | 六大组件围绕"可信上下文/来源归因总线"协同 |

| 责任可追溯、过程可审计             | 政企刚需      | 防篡改证据链 + 来源归因溯源               |

## 2. 总体架构:透明安全网关 + 策略驱动管线 + 来源归因总线

主干形态采用**透明安全网关(Transparent Security Gateway)**——调研中赢家(Invariant Gateway、agentgateway+Langfuse、"独立于模型的基础设施级强制点")的共同选择,满足"无侵入 + 兼容"。

**接入边界(务实分级,而非"只卡两点"):**

- **首要边界**:**OpenAI 兼容的 LLM API** + **MCP 工具**。原型阶段优先、完整覆盖这两类。
- **补充边界**:真实智能体常有**非 MCP 工具**(本地函数、浏览器驱动、文件系统 SDK、Python tool、非 MCP 插件)。这些通过**工具适配器**接入,统一进入 ② 工具调用管控与**沙箱执行器**。
- 对**确实绕过网关**的路径(直连模型、自带工具),架构不假装能拦截,而是在 §7 给出**检测与降级策略**(异常发现 + 审计标记 + 运营告警),并在文档中诚实声明边界。

## 5. 核心机制:可信上下文 / 来源归因总线 —— 枢衡的脊柱

这是枢衡相对所有标杆的**核心差异化**,作为架构脊柱而非附加功能。**但措辞要诚实**:

- **来源标注(确定性强)**:任何输入进入网关时,标注 `信任级别`(可信/半可信/不可信)+ `来源`(用户/网页/文档/检索/记忆/工具返回)。这一步是确定的,可严格落地。
- **证据化归因(带置信度,不是形式化 taint)**:LLM 是非透明变换,**无法严格证明**某个工具调用参数一定来自某段不可信输入。因此模型产出工具调用后,我们用**多证据加权**给出"该调用受哪条不可信输入影响"的**置信度**:
  - 来源标签传递(上下文里是否存在不可信片段)
  - 上下文片段匹配 / 参数与输入的**相似度**
  - 结构化引用(若智能体显式引用了来源)
  - **LLM-judge 归因**(让裁判模型解释依据)
- **判定**:策略据"不可信来源 × 高危动作 × 归因置信度"分级处置。
- **溯源**:审计时反查"某次危险调用 → 高可能由哪条不可信输入引发",输出**带置信度的归因链**,实现可解释的责任追溯。

> 这样既保住差异化(业界普遍做不到归因溯源),又不夸大为"形式化污点传播"——答辩经得起追问。评测中用**溯源命中率**量化其有效性(见评测指标体系)。

| 层               | 选型                                                    |

### 6.2 终局增强(M4 及之后,可替换/后置)

| 项         | 增强                                                       |
| ---------- | ---------------------------------------------------------- |
| 向量相似度 | pgvector / FAISS(Rebuff 式已知攻击库)                      |
| 检测       | LLM-as-judge 归因、AlignmentCheck 式对齐审计、多检测器融合 |
| 供应链     | Semgrep 代码扫描 + 依赖图 + 行为启发式                     |
| 审计       | PostgreSQL + 完整 OTEL 链路、对接 Langfuse                 |

| 控制台     | 策略编辑、多角色权限、告警、大盘美化                       |

### 6.3 沙箱执行器 MVP 边界(不是开放问题)

命令/文件/浏览器是榜题点名高危,MVP 必须落地一个**真隔离**执行器,最小边界:

- **隔离**:容器(优先)或受限子进程(降级);独立用户/命名空间
- **文件**:工作目录**只读挂载** + 显式可写白名单;**路径白名单**,涉密路径直接拒绝
- **网络**:默认**关闭外联**,按策略白名单放行
- **资源**:CPU/内存上限 + **执行超时**强制终止
- **审计**:执行前后快照写入审计链

## 7. 失败模式与降级策略

透明网关并非万能,必须明确"何时会失效、如何降级",这是企业级与答辩可信度的关键。

| 失败模式                         | 影响       | 降级 / 应对                                                     |
| -------------------------------- | ---------- | --------------------------------------------------------------- |
| 智能体**绕过代理**直连模型 | 防护被旁路 | 部署侧限制出口(仅允许经网关);审计侧检测"无网关记录的行为"并告警 |
| 工具调用**不走 MCP**       | 漏管控     | 工具适配器纳入;无法适配者标记为"不可控来源",策略默认收紧        |
| 模型**流式输出中断**       | 检测不完整 | 缓冲到可判定单元再放行;超时按"未通过"处理(fail-closed)          |
| **审批超时**               | 任务卡死   | 可配置:默认 fail-closed(拒绝),关键链路可设升级通知              |
| **审计写入失败**           | 证据缺失   | 本地落盘兜底 + 重试队列;审计不可用时高危动作**默认阻断**  |
| **策略服务不可用**         | 无法判定   | fail-closed:除白名单低危动作外一律阻断,并告警                   |
| 检测**误杀(高 FPR)**       | 影响可用性 | 分级处置(净化/审批优先于阻断)+ 控制台一键放行 + 样本回流优化    |

> 总原则:**安全关键路径 fail-closed,可用性路径 fail-open 但留痕**;具体取舍可在策略中配置。

### 7.1 部署侧强制:防旁路运维清单(不做等于白装)

上表首行「智能体绕过代理直连模型」是内联网关的命门:被注入或被攻陷的智能体会主动绕开网关。**整套防护的承重假设是"智能体除经网关外到不了 upstream"**——它由**凭证隔离**或**网络出口封锁**兜底(至少其一),再以**审计对账**探测漏网(补偿)。下表按优先级列出落地项,并标明每项归属:**Fulcrum 提供**(点名端点/机制)、**运维基建**(部署方自建,产品给不了)、或**尚未落地**(诚实声明边界,勿当已有能力,见 §报告 诚实边界原则)。

| 优先级 | 项 | 归属 | 做什么 / 如何验证 |
| ------ | ---- | ---- | ----------------- |
| 🔴 P0 | 出口封锁 | 运维基建 | 智能体容器仅允许出向网关地址;upstream 域名(openai/anthropic/本地 Ollama 端口)只对网关放行。**验证**:智能体容器内 `curl api.openai.com` 应失败 |
| 🔴 P0 | 客户端指向网关 | Fulcrum 提供 | LLM SDK `base_url` → 网关 `POST /v1/chat/completions`(OpenAI 兼容内联代理,先过双向检测再转发上游);工具经 `POST /tools/call`。**验证**:调用后 `session_id` 出现在审计链 |
| 🔴 P0 | upstream 凭证只在网关 | 部分·运维 | 真实 API Key 仅注入网关进程,智能体侧环境**不给** key(注入侧即便想直连也无凭据)。**验证**:智能体容器 env 无 upstream key |
| 🟡 P1 | DNS 兜底 | 运维基建 | 内网 DNS 把模型 API 域名解析到网关,防硬编码地址绕过 |
| 🟡 P1 | 工具统一入口 | Fulcrum 提供 | 高危工具(shell/file/http.request/browser)强制经 `RestrictedExecutor` 沙箱,禁智能体自起子进程 |
| 🟡 P1 | 审计对账告警 | 运维基建 | 监控「有模型/工具行为但网关无记录」→ 即时告警(日志聚合/进程审计/eBPF 皆可)。**这是下方未落地项的补偿探测层** |
| 🟢 P2 | 策略变更管控 | 运维基建 | 策略为声明式 YAML(§8)、纳入版本控制,变更走 git 评审 + CI(运行时无编辑端点);每次判定留 `POLICY_DECIDED` 审计,放行/阻断可追溯 |
| 🟢 P2 | 定期回放 | Fulcrum 提供 | 用 `samples/` 攻击样例集定期跑 `python -m fulcrum.eval`,确认防护未随迭代退化 |

> **两项当前尚未落地的硬化方向(诚实边界,勿当已有能力)**:① **影子 key 兑换**——数据面 `/v1/chat/completions` 现无鉴权,尚无 per-agent 签发/兑换真实调用的机制;可实现的半步(upstream key 只在网关、智能体侧无 key)见 P0。② **智能体注册清单**——数据面无身份闸(`session_id` 默认 `anon`),未注册身份无法拒绝,调用亦无法归因到具体智能体;现有 RBAC 仅覆盖控制台。二者共同指向后续「数据面加轻量 agent-token 鉴权」——落地后 P0 的凭证隔离与 P2 的智能体清单即同时成立。

## 8. 策略引擎:最小语法示例

自研轻量声明式策略(YAML),核心是 `条件 → 处置`,条件可引用**来源信任级别、动作类型、参数、归因置信度**。示例:

```yaml
# 1. 不可信来源不得驱动文件读取 / 外部 HTTP 调用
- when:
    source_trust: untrusted        # 来源不可信
    action: [file.read, http.request]
    attribution_confidence: ">=0.6" # 归因置信度达阈值
  then: block

# 2. 高危系统命令一律人工审批
- when:
    action: shell.exec
    risk: high
  then: require_approval

# 3. 涉密路径直接阻断(最高优先级)
- when:
    action: [file.read, file.write]
    path_matches: ["/secret/**", "**/*.key", "**/涉密/**"]
  then: block
  priority: 100

# 4. 任务链异常:同一会话短时高频外联 → 审批
- when:
    chain_pattern: "read_sensitive -> http.request"
    window: 60s
  then: require_approval
```

> 这套"声明式 + 风险分级 + 归因条件"既能表达细粒度权限,又能讲清楚动态策略与审批条件,落地与答辩都好交代。

## 9. 端到端数据流(一次请求的全链路)

```
1. 智能体发起 LLM 请求(含用户输入 + 网页/文档/检索/记忆)
   └► C1 LLM代理截获 ─► C2a 输入扫描 + 来源打标(写入来源归因总线)
2. 模型返回"工具调用意图"(或经 MCP/适配器发起真实调用)
   └► C2b 工具风险评分 + 任务链分析 ─► C3 策略中心判定(含归因置信度)
3. 分级处置(C4):
   allow ─► 放行   |  净化 ─► 改写参数   |  需审批 ─► 推送控制台人工确认   |  阻断 ─► 拒绝
4. 放行的高危调用 ─► C4x 沙箱执行器(新工具先过 C5 供应链扫描)
5. 全过程写入 C6 防篡改审计链(含带置信度的归因链路)
6. 评测模式:C6 评测引擎回放攻击样例,统计 ASR/误报漏报/阻断率/审计完整率/溯源命中率
7. C7 控制台:事件列表 + 审批队列 + 审计溯源 + 评测报告
```

## 11. 范围与分期(供应链前移 + 控制台演进)

| 阶段                             | 目标                                                             | 关键产出                                |
| -------------------------------- | ---------------------------------------------------------------- | --------------------------------------- |
| **M1 主干贯通**            | 网关 + 来源打标 + 基础检测 + 审计 +**供应链最小扫描** 跑通 | 拦一种注入并审计;扫一个 manifest 出评级 |
| **M2 防护内核**            | ①② 做深:多源检测、工具管控、审批、任务链、沙箱执行             | 政务办公场景攻防闭环                    |
| **M3 评测出分**            | 评测引擎 + 中文样例集 + 量化指标                                 | ASR/误报漏报/阻断率/溯源命中率报告      |
| **M4 控制台 + 供应链增强** | 完整控制台 + Semgrep/依赖/行为分析                               | 演示视频主体 + 一体化补全               |

**供应链(③)修正**:大方向要求"轻量做全",故 **M1 即做最小闭环**(manifest/权限/可疑描述/外联依赖→评级),Semgrep/依赖图/行为启发式作为 M4 增强,避免后期来不及导致榜题缺角。

**控制台演进说明**:早期 MVP 子集曾限定为 4 页(风险事件、审批队列、审计溯源、评测报告),用于控制范围。当前实现已扩展为完整运营控制台,并通过 `FeatureModule` 注册表统一接入导航、路由、权限和备份资源。网关实测、评测验证等答辩/开发者页面默认隐藏,由系统设置中的开发者模式开启;管理员日常视图保持干净。

## 12. 风险与开放问题(待后续决策)

1. **被保护智能体选型**:候选需满足"OpenAI 兼容 API + MCP + 含文件/命令/浏览器/接口工具 + 活跃 + 许可宽松"。候选:OpenManus / OpenHands / Open Interpreter / MCP 原生 Agent。→ 进入实现前确定。
2. **中文检测模型**:PromptGuard 等偏英文,中文注入/越狱检测可能需微调或换中文基座。→ 评测阶段验证。
3. **归因置信度阈值标定**:证据化归因的权重与阈值需用样例集调参,避免高 FPR。→ M3 评测中标定。
4. **完整控制台工时**:已用分期对冲,M4 仍需留足前端预算。

> 已"降级"的开放问题:沙箱(→ §6.3 已定边界)、供应链排期(→ M1 前移)。
