## 0. 设计目标:在不可信网络里也站得住

私有化单租户不等于"内网就安全"。本设计按"凭证库会泄、网络会被嗅探、口令会被爆破"来兜底:

- **口令只存哈希,且抗爆破**——库被拖走也还原不出明文。
- **会话用不透明令牌,且库内只存其指纹**——库被拖走也伪造不出有效会话。
- **令牌只走 HttpOnly Cookie**——前端 JS 读不到,XSS 也偷不走。
- **失败有锁定、信息不泄露**——挡暴力破解,且不暴露"账号是否存在"。

## 1. 口令存储:Argon2id

| 维度 | 取值 | 为什么 |
| --- | --- | --- |
| 算法 | **Argon2id** | OWASP 口令哈希首选、PHC 冠军;内存硬,抗 GPU/ASIC 并行爆破,id 变体兼抗侧信道 |
| 内存成本 | 64 MiB | 抬高单次爆破成本的主力;政企单机内存充裕,可按硬件上调 |
| 时间成本 / 并行度 | 3 轮 / 4 | OWASP 2024 建议基线 |
| 盐 | 16B,库自动生成 | 每条口令独立盐,编码进自描述哈希串,无需另存 |

- 明文口令**只在内存中短暂存在**:不落库、不进日志、不入审计。
- 哈希串自描述(含算法+参数+盐),校验按串内参数重算;调参后旧串仍可校验。
- 登录校验通过且检测到旧参数 → **透明重哈希**(`needs_rehash`),无感升级强度。

实现:[`passwords.py`](../../src/fulcrum/adapters/auth/passwords.py)。

## 2. 会话:服务端不透明令牌

不用 JWT。私有单租户下,**服务端会话**比自包含令牌更安全——可即时撤销、不在客户端携带任何机密。

- 登录签发 `secrets.token_urlsafe(32)`(**256bit** 随机),作为原始令牌仅此一次经 `Set-Cookie` 下发。
- 库内**只存 `SHA-256(令牌)`**:即便会话表被读走,也反推不出可用令牌(单向)。
- 校验:Cookie 里的令牌取 SHA-256 → 命中且**未过期、用户未停用**才放行。
- 退出 = **删服务端会话行**(不是只清 Cookie);过期会话在每次登录时顺带清理。

实现:[`service.py`](../../src/fulcrum/adapters/auth/service.py) · [`store.py`](../../src/fulcrum/adapters/auth/store.py)。

## 3. Cookie 三道闸

`Set-Cookie` 携带 `fulcrum_session`:

| 属性 | 值 | 作用 |
| --- | --- | --- |
| `HttpOnly` | 恒开 | JS 读不到 → XSS 偷不走令牌 |
| `SameSite` | `strict` | 跨站请求不带 Cookie → 挡 CSRF |
| `Secure` | TLS 后置 `true` | 只在 HTTPS 回传 → 防明文嗅探(本机 http 调试置 false) |
| `Max-Age` | 会话有效期 | 绝对过期,到点强制重登 |

前端**全程不接触令牌**:`lib/auth.tsx` 只凭 `GET /auth/me` 判断"登没登上",只持有用户名/显示名这类非敏感信息,无 `localStorage`。

## 4. 抗暴力破解 / 抗枚举

- **锁定**:同一账号连续失败达 `FULCRUM_LOGIN_MAX_FAILURES`(默认 5)→ 锁定 `FULCRUM_LOGIN_LOCKOUT_MINUTES`(默认 15),期间一律 `429`。计数落库,重启仍生效。
- **抗用户枚举**:账号不存在时也跑一遍等价 Argon2 校验(耗时对齐),且登录失败统一回 `账号或口令错误`——不暴露是账号错还是口令错。

## 5. 接口

| 方法 | 路径 | 说明 | 失败 |
| --- | --- | --- | --- |
| POST | `/auth/login` | 体 `{username, password}`;成功下发会话 Cookie,返回 `{username, display_name}` | `401` 凭证错 · `429` 锁定 |
| POST | `/auth/logout` | 撤销服务端会话并清 Cookie | `204` |
| GET | `/auth/me` | 返回当前主体;受 `require_auth` 守卫 | `401` 未登录/已失效 |

`require_auth` 依赖挂在 `app.state`,供后续受保护路由复用——M4 接 RBAC 时在其之上叠权限点校验。

## 6. 部署与首次引导

- **同源**:生产由后端托管前端静态资源(单容器),前端用相对路径调接口,Cookie 天然同源。开发期 Vite 反代 `/auth` 等到后端(见 [`vite.config.ts`](../../console/vite.config.ts)),开发/生产一致。
- **首启管理员**:库内无用户时,据 `FULCRUM_BOOTSTRAP_ADMIN_USERNAME/PASSWORD` 创建。**口令留空 → 随机生成并在日志打印一次**,请立即登录修改。口令绝不写死在源码或镜像里。
- 配置项见 [`.env.example`](../../.env.example);用户/会话库默认 `data/runtime/auth.sqlite`,与审计库分离。

## 7. 边界与后续

- **RBAC 已落地**:组织架构 + 自定义角色权限 + 成员生命周期 + 申请审批见 [用户管理与权限](06-用户管理与权限.md);不同权限看到不同界面、后端按权限点强制鉴权。
- 加用户 / 改派:走管理后台(申请审批或管理员直建);**自助改密**(个人中心)待排期,当前改密走管理员"重置口令"。
- TLS 由部署侧(反代/网关)负责;启用后务必置 `FULCRUM_SESSION_COOKIE_SECURE=true`。
- 登录事件目前走结构化日志;接入 hash-chain 审计为后续项。
