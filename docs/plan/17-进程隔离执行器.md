# 枢衡 Fulcrum · 进程隔离执行器

> 本文回答:在不依赖 Docker 的前提下,`restricted` 执行器提供哪些真实可终止边界、如何配置和验证。
> 状态:草稿 v1 · 2026-07-15。

## 范围

`RestrictedExecutor` 保持既有 `Executor`/`Tool` 契约不变。通过预检后,工具调用在独立的
`multiprocessing` `spawn` 子进程中执行,而非线程池。父进程在墙钟超时后终止 worker;POSIX
还会终止其独立进程组。子进程将当前工作目录设为配置的 `workspace`,并在 IPC 发送前截断输出。

默认 `allow_network: false`,worker 会拦截 Python 标准 `socket` API。开启网络还必须经既有
`allow_domains` 域名白名单和 URL 协议检查。CPU 与内存限制使用 POSIX `setrlimit`;Windows 尝试使用
Job Object 的进程时间和内存上限。若宿主已将进程置于不允许嵌套的 Job,结果会标记
`sandbox_resource_limits: wall_clock_input_output_only`,并保持进程终止和体积边界。默认值见
[fulcrum.yml](../../src/fulcrum/config/fulcrum.yml)。

## 最小验证

```powershell
uv run pytest tests/test_restricted_executor.py -q
```

测试仅使用进程 ID、工作目录、`sleep` 后写入工作区标记文件，以及不连接任何地址的 socket 构造。
它验证子进程执行、工作目录、默认网络拒绝、输出/输入边界及超时后不会发生延迟写入。

## 明确边界

- 危险命令、敏感/越界路径和不合规 URL 仍由执行前的既有 fail-closed 规则拒绝。
- 这是 Python 工具调用的最小进程边界,不是虚拟机、容器或网络命名空间。恶意原生代码、绕过 Python
  socket 的网络库及特权系统调用不在本实现的隔离保证范围。
- `spawn` 要求工具对象可序列化;无法启动子进程时执行器拒绝调用,不会回退到线程或进程内执行。
- 未在本次改动中执行 Docker 构建或任何真实外联/攻击命令。
