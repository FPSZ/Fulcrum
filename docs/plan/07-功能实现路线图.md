## 0. 排序依据(为什么是这个顺序)

赛题评分:**实际效果 30% · 技术创新 25% · 方案完整性 20% · 应用价值 20% · 展示表达 5%**。
关键约束:**9/15 24:00 截止**,交付 = 技术报告 PDF(≤30 页)+ 代码仓库 + 演示视频(≤10min)+ 报名表。

三条铁律决定优先级:

1. **30% 的"实际效果"= 量化指标**(攻击识别准确率、误报漏报、阻断率、审计完整性)。这些数字**只能由"真实防护闭环 + 评测引擎"产出**。所以 P0 不是控制台、不是占位页,而是**把后端桩换成真实现并跑出数字**。
2. **能演示 > 功能多**。评委看的是 10min 视频 + 现场答辩。一条"恶意文档→高危工具→阻断→审计可溯源→评测出分"的完整链路,胜过十个半成品页面。
3. **四大赛题目标要都覆盖到**(方案完整性 20%),但**深度优先于广度**:目标①②(识别+管控)做深拿"实际效果",目标④(评测审计)是出分载体必做,目标③(供应链)做**最小可信闭环**即可覆盖面。

> 一句话:**先让它真的拦得住、并能给出分数,再让控制台把这件事讲好看,最后补供应链与创新点。**

## P0 ── 端到端防护闭环 + 出分(命脉)

> 对应赛题目标 ①②④ · 评分:实际效果 30% + 技术创新 25% 的地基。
> 完成标志:`pytest` 全绿 +「跑一条命令,打印 Baseline vs Fulcrum 的 ASR/FPR/阻断率/审计完整率/溯源命中率」。
> 做法:**填 `src/fulcrum/capabilities/` 既有插槽,不改核心管线**(对称于前端插件系统)。

### P0-a 防护内核最小真链路(把桩换成真实现)

- [ ] 确认/补齐领域类型:`SourceSpan`(多源+信任级+风险标签)、`ToolIntent`、`PolicyDecision`、`AuditEvent`、`EvalSample`(`core/domain/models.py`)
- [ ] **输入检测**:扩展 `capabilities/detectors/keyword_rules.py` → 多源(用户/文档/网页/检索/记忆/工具返回)+ 提示注入/越狱/泄露/外发/命令执行 关键词 + 风险标签 + 分级
- [ ] **来源标注**:`labelers/passthrough.py` → 给每个来源打 `SourceSpan`(信任级 trusted/semi/untrusted + content_hash + excerpt)
- [ ] **归因**:`capabilities/attribution/zero.py` → 真实现:工具参数/路径/URL/命令 与不可信来源片段相似或同会话相邻 → `derived_from_sources` + 0~1 置信度
- [ ] **工具风险评分**:`capabilities/toolguard/zero_scorer.py` → 真实现:文件路径敏感度 / URL 白名单 / 命令危险度
- [ ] **策略引擎**:`capabilities/policy/allow_all.py` → YAML 策略(`data/policies/default.yml`),支持条件 `source_trust / tool_name / risk_level / path_matches / domain_allowed / command_risk / attribution_confidence`,产出 `allow / sanitize / approve / block`
- [ ] **审计链**:`adapters/audit/memory_sink.py` → SQLite + hash-chain(`event_hash = sha256(prev_hash + canonical_json(event))`),`data/runtime/` 不入库
- [ ] 在 `core/pipeline.py` 里把以上接成:`接收→标源→检测→归因→策略判定→处置→审计` 一条用例(管线编排不动,只换实现)
- [ ] 单测:detectors / attribution / toolguard / policy(优先级+判定)/ audit(hash-chain 写入+校验 100%)

### P0-b 工具网关与受控执行

- [ ] 内置 4 个受控工具:`file.read / file.write / http.request / shell.exec`(`capabilities/tools/`),约束见 [02-MVP §4](02-MVP.md)
- [ ] 受控执行器:`capabilities/sandbox/echo_executor.py` → 真实现(file/http 限 demo workspace + 域名白名单;shell 默认 require_approval、危险命令直接 block)
- [ ] Tool Gateway:`POST /tools/call`(`adapters/api/`),走完整「评分→策略→执行/审批/阻断→审计」
- [ ] 集成测:正常 file.read 放行 · 不可信文档驱动的高危调用被 block · shell.exec 走审批不实际执行

### P0-c LLM 代理 + demo Agent(让闭环变成"政务场景")

- [ ] LLM Proxy:`POST /v1/chat/completions`(OpenAI 兼容,非流式优先)——抽取来源→检测→转发真实模型→捕获 tool_call→转 `ToolIntent`→策略→审计
- [ ] 极小政务办公 Agent(`demo/`):读"群众来信/政策材料"→ LLM 摘要 → 触发 file.read / http.request,全程过枢衡
- [ ] 两条演示链路:**正常文档**(放行)/ **恶意文档**(藏"读 secret 并外发"的间接注入 → 阻断 + 审计证据)

### P0-d 评测引擎 + 中文样例集(出分,实际效果 30% 的载体)

- [ ] 评测入口:`python -m fulcrum.eval --dataset samples/eval/core.json --out docs/eval/results/latest` → `metrics.json / details.jsonl / report.html`
- [ ] 中文脱敏样例集(≥20 条):5 benign · 5 direct_injection · 5 indirect_injection · 3 unauthorized_tool · 2 malicious_manifest
- [ ] Baseline 对照:`--mode baseline` 禁用策略阻断,只记录攻击是否成功
- [ ] 核心指标产出:`ASR_baseline / ASR_fulcrum / ASR 降幅 / Recall(BSR) / FPR / Utility / 高危动作处置正确率 / 审计完整率 / Source Hit@1·@3`
- [ ] 对照 [eval/00 评测指标体系](../eval/00-评测指标体系.md) 校准口径

> ✅ **P0 验收**(也是演示视频骨架):①正常任务不误伤 ②恶意文档高危调用被阻断 ③审计详情可说清"哪段输入→哪次调用→哪条策略→什么处置" ④评测报告展示 Baseline 与 Fulcrum 的 ASR 差异。

## P2 ── 供应链最小可信闭环(覆盖赛题目标③)

> 对应赛题目标 ③ · 评分:方案完整性 20%(覆盖面)。
> 完成标志:能扫一个恶意 MCP/Skill manifest 并给出 `allow/review/block` 评级 + 控制台可见。

- [ ] 扫描命令:`python -m fulcrum.supplychain scan samples/supplychain/*.json`(`capabilities/supplychain/noop.py` → 真实现)
- [ ] 检测项:工具描述含提示注入 · 高危权限(文件/命令/网络)· 声明外联 URL · 可疑命令/下载行为 → 评级
- [ ] 脱敏样例:恶意 manifest × 2 + 正常 × 2,纳入评测集(算供应链恶意组件召回率)

## P3 ── 创新与加分项(技术创新 25%,挑性价比高的做)

> 对应技术创新 25% + 应用价值。**按时间余量取舍,不必全做**;每项都是独立加分点。

- [ ] **LLM-as-judge 增强**:在规则检测之上叠模型研判(提升注入识别 Recall、降低 FPR)——直接抬"实际效果"数字
- [ ] **异常任务链阻断**:多步工具调用的跨步关联(本步参数源自上一步不可信返回值 → 阻断),对应目标②"异常任务链阻断"
- [ ] **RBAC 权限组**:按 [05-控制台能力规划](05-控制台能力规划.md),让管控/审批落到角色闸门

- [ ] **沙箱执行强化**:从 echo 受控执行 → 真实受限执行(边界见架构总览 §6.3)
- [ ] **单容器部署**:按 [04-单容器部署方案](04-单容器部署方案.md),后端托管前端 + Dockerfile,一条命令跨平台起服务(利于评委复现 → 实际效果/应用价值)
