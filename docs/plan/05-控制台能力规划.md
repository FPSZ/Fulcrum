## 1. AI 操作助手(可操控软件的助手)

### 1.1 目标

控制台内置的 AI 助手**不止能对话,还能代操作软件**。管理员用自然语言下达意图,助手自动把它翻译成控制台动作并执行。例如:

- "帮我打开安全网关设置" → 助手导航到 设置 / 安全网关 面板。
- "把实时事件按严重等级筛一下,只看阻断" → 助手切到实时事件页、设好筛选与分组。
- "把 POL-014 这条策略临时停用" → 助手定位策略 → **高危动作,弹确认** → 操作员确认后执行并写审计。

定位:它是"会按钮的副驾",降低值班操作门槛;不是替操作员做安全决策。

### 1.2 与现有架构的对接:动作注册表(对称功能模块注册表)

复用我们已有的"注册表 + 一行装配"思路(后端 `@capability`、前端 [功能模块插件系统](../arch/02-前端骨架与扩展规范.md))。新增一层**动作注册表**:

- 每个可被 AI 调用的动作声明:`id` / `label` / 给 LLM 看的 `description` / 参数 `schema`(zod)/ `handler` / `risk`(只读·一般·高危)/ `requires`(所需权限,见 §2)。
- 动作就近挂在它所属的**功能模块**上(给 `FeatureModule` 增补可选 `actions?` 字段),模块注册时动作一并进表 —— 加页面即自动获得"可被 AI 操作"的能力,**助手代码零改**。
- 助手用 LLM 的 **function-calling** 对着这张表选动作、填参数;执行即调用对应 `handler`(导航、设筛选、开面板、提交审批等)。

### 1.3 安全模型(本项目尤其要自洽)

我们是做智能体安全的,**自己的 AI 助手更要被治理**——这正好是对评委可讲的"吃自己的狗粮":

1. **走自家网关**:助手的模型请求经**枢衡 LLM 网关**转发,本身就被输入检测/策略/审计覆盖。
2. **分级执行**:`只读/导航`类动作可自动执行;`高危`动作(改策略、放行/阻断、改网关配置、管成员)**必须二次确认**,并显示"将要执行什么"。
3. **权限内执行**:助手只能调用**当前操作员权限组允许**的动作(与 §2 联动);越权请求直接拒绝并说明。
4. **全程审计**:每次 AI 发起的动作写审计事件(谁、经由助手、做了什么、命中哪条确认),纳入 hash-chain。

### 1.4 入口与边界

- 入口复用侧栏已有「AI 安全研判 / 打开研判台」卡片,扩展为"对话 + 操作"面板。
- MVP 范围(首版落地):动作表先覆盖**导航 / 筛选 / 打开面板**等只读类;高危写操作排后,且默认走确认。
- 不做:让助手自主连续多步执行无人确认的高危链;不做跨系统的外部操作。

## 2. 权限组(RBAC:不同权限看到不同界面)

### 2.1 目标

按**权限组(角色)**区分能看什么、能做什么。不同角色登录后,**界面内容、可见页面、可用动作都不同**。契合政企治理的**最小权限 / 职责分离 / 可审计**要求。

示例角色(私有化单租户内部):

| 角色 | 典型可见/可做 |
| --- | --- |
| 管理员 | 全部页面 + 网关/成员/数据配置 + 高危动作 |
| 安全审计员 | 审计溯源、实时事件(只读)、评测报告;不可改策略/网关 |
| 值班操作员 | 实时事件 + 审批处置 + 工具网关;不可管成员/改全局配置 |
| 只读访客 | 总览 + 只读事件;无任何写操作 |

> 具体角色与权限点最终在设置页「成员与权限」面板维护,本表只是示例。

### 2.2 与现有架构的对接:模块/动作按权限过滤

- **权限点**:定义细粒度权限(如 `event.read` / `event.approve` / `policy.edit` / `gateway.config` / `member.manage` / `ai.operate`)。角色 = 权限点集合。
- **功能模块按权限过滤**:给 `FeatureModule` 增补可选 `requires?`(所需权限)。`getFeatures()` 按当前用户权限过滤 —— **侧栏导航、路由自动只显示有权的页面**,无权页面不出现/不可达。
- **页面内再细分**:页面内的敏感区块/按钮(如"批量处置""新建策略")按权限点条件渲染。
- **动作表联动**:§1 的 AI 动作也带 `requires`,助手能调的动作即"当前角色能点的按钮",两套机制共用同一套权限点。

### 2.3 安全模型(前端只是体验,后端才是闸门)

1. **后端强制授权**:每个 API 按调用者角色校验权限;**前端隐藏 ≠ 安全**,绕过前端也必须被后端拒。前端过滤只为"干净的界面"。
2. **会话即角色**:登录(接后端 `/auth` 后)拿到角色/权限点,前端据此过滤;令牌/会话不落前端源码。
3. **变更可审计**:角色与权限的变更本身写审计,满足责任追溯。

### 2.4 边界

- MVP 先做"角色 → 页面可见性 + 关键写动作开关"的粗粒度;字段级/数据行级权限排后。
- 单租户内部 RBAC,不做多租户隔离(与项目定位一致)。

---

## 3. 两者的关系

权限组是**地基**,AI 操作助手是**长在地基上的副驾**:助手能做的事 = 当前角色被授权的动作集合。落地建议**先做权限组(§2)**,再做 AI 操作助手(§1),让助手从第一天起就在权限闸门内运行。
